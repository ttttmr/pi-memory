# 记忆的构成与运行逻辑

[English](design.md) | 简体中文

本文从文件和消息的关系出发，说明一次经验怎样被保存、再次使用，以及独立 dreaming 怎样维护这些内容。使用入口见 [README](../README.zh-CN.md)，具体参数见[工具参考](tools.zh-CN.md)，测试方法见[开发指南](development.zh-CN.md)。本页示例均为合成场景，不代表真实模型评测。

## 先区分持久知识与运行时材料

pi-memory 的持久知识是 Markdown，模型通过读取文件获得这些知识，不涉及模型权重更新。当前项目和全局分别有一套索引和正文。前台 Agent 可维护两种作用域，后台 dreaming 只维护同一套项目文件，不另建总结库。

| 组成 | 保存在哪里 | 作用与读取方式 |
| --- | --- | --- |
| 主题笔记 | 所选作用域里的普通 `.md` 文件 | 保存结论、条件、依据和假设；通过 `memory_search` 找到、`memory_read` 读取 |
| 入口索引 | 所选作用域的 `MEMORY.md` | 少量导航和高价值提示；前台请求默认自动带入，后台按需用工具读取 |
| 修订历史 | 同目录下的 `.history/` | 保存改写、归档前的正文；不参与活动搜索，不通过记忆工具读取 |
| 归属元数据 | 同目录下的 `.identity.json` | 记录项目 identity 和作用域，供程序防止目录误用；不是知识正文 |
| 项目调度元数据 | 项目目录下的 `.dream-state.json` | 保存实际用户消息 ID、待处理会话批次、legacy 工作和运行租约；记忆工具不可读取 |
| 原生会话历史 | 由 Pi 管理的同项目会话文件 | Agent 自主读取原始历史，不另存来源会话副本 |
| dreaming 对话 | `.dream-runs/` 下的运行目录 | worker 自身原生会话、JSONL 事件、状态和 supervisor 诊断，与前台对话分开 |

索引、主题笔记和来源不是同一个东西。索引回答“什么时候该看哪份笔记”，笔记回答“当时得到了什么结论，依据是什么”，来源是模型需要回头核对的材料。笔记中的引用由模型写入，不会自动附上完整日志。后台 Agent 可以通过会话 ID 与文件提示定位同项目原始历史，但文件缺失或未落盘都可能使来源不可用，不能把引用本身当作已核验。

`.history/` 也不能充当这个证据库：它保留的是笔记曾经怎么写，不是当时实验或文档必然正确的证明。

```text
前台上下文中的要求、观察和反馈
              |
              | 前台 Agent 选择有复用价值的知识
              v
       主题笔记 <--- MEMORY.md 中的路径链接
          ^                  |
          |                  | 前台请求前自动加载小索引
          |                  v
          +--- memory_read --- 前台模型判断是否使用
          |
          +--- 后台 dreaming 回查同项目历史、创建和维护同一批文件
```

图中的两种模型运行都可以修改笔记，但只有前台模型还在执行用户的普通任务。dreaming 被要求只做记忆维护，但拥有普通 Agent 工具；这是提示策略，不是工具沙箱。

## 前台一次请求中发生什么

### 加载扩展不会立即生成知识

扩展注册 `memory_search`、`memory_read`、`memory_write`。唯一的用户命令 `/memory <自然语言说要记住的一件事>` 将用户原话作为供未来轮次和会话使用的保存请求交给前台模型；前台忙时排为 follow-up。空参数只显示用法，不调用模型。命令处理器不直接生成笔记，模型自主选择如何调用记忆工具。

前台写入指导只说明记忆用于未来轮次和会话：用户要求时，或有明显值得记住的内容时保存，具体保留什么、怎样组织留给模型判断。不规定笔记类别、必填段落或统一维护步骤。工具说明仍解释路径、分页、哈希和索引等操作要求；搜索指导保留相关时查阅记忆、核对适用性和不把记忆当作更高优先级指令的提醒。独立 dreaming 使用后文所述的维护任务提示，不把整套后台流程塞进前台常驻规则。

`session_start` 根据启动参数设置召回与自动 dreaming 开关，不清空记忆文件，也不重置项目级待处理用户消息计数。`--pi-memory-no-recall` 和 `--pi-memory-no-dream` 分别关闭召回与自动整理；恢复时需不带相应关闭参数重启 Pi，没有运行时切换命令。只读启动与读取缺失记忆不创建目录。首次记录新的实际用户消息时，可以建立项目目录、归属和调度文件，即使尚无 Markdown 笔记；知识正文仍由模型决定是否创建。写入中途失败也可能留下已创建的目录。

### 模型请求前，插件只加载入口

`context` 钩子在默认启用召回、项目已受信任且消息中存在 user 请求时执行：

1. 取本次消息副本，去掉其中已有的本扩展临时索引消息，避免反复累加。
2. 从当前项目与全局目录读取各自的 `MEMORY.md`。
3. 把非空索引及历史资料提示，临时放到最近一条 user 消息之前。
4. 将这份消息副本交还 Pi，继续正常模型请求。

这里没有按问题做关键词查询，也没有展开索引中的链接。每个索引最多 8 KiB、200 行，正文留待模型决定是否读取。不存在或空白的索引不注入；读取失败时提示错误并跳过本次注入，不阻断前台任务。

临时索引不追加到持久会话、不替换系统提示、不修改压缩过程。下一次请求会重新读当前文件，因此模型能看到期间发生的修订。项目与全局索引都只是参考，没有项目自动覆盖全局的规则，也没有程序替模型裁决矛盾。

### 模型沿着线索读正文，或主动搜索

知道路径时，模型调用 `memory_read`。索引不全、路径不明或需要找其他相关笔记时，可以用 `memory_search`。二者互补，不是每次必须先搜索再读取。

搜索遍历活动 Markdown 的路径和正文，不搜索 `.history/`，也不查询原始会话。英文按词提取查询项，连续汉字和日文假名使用相邻双字，单字片段保留单字。每个不同查询项命中路径加 4 分、命中正文加 1 分，重复出现不叠加；同分按路径、作用域排序。没有有效查询项时列出路径。

搜索返回路径、哈希和摘录，读取工具再返回正文及完整文件的哈希。较长正文先按行选范围，再按 Unicode 码点分页，单页 content 最多 8 KiB；完整协议见[工具参考](tools.zh-CN.md#memory_read)。这些工具结果会像其他工具结果一样进入前台会话，和临时索引的生命周期不同。

### 做任务得到新反馈后，模型决定是否保存或修订

前台可以利用本次任务原本允许的工具获得测试、文档或用户反馈，再判断哪些值得保留。适合记忆的内容不限于失败，也包括成功方法、稳定偏好、重要决定和有条件的计划。轻易能重新读取的动态状态、完整流水账、秘密和 AGENTS.md 副本不适合保存。

模型调用 `memory_write` 时提交完整 Markdown，正文结构和组织由模型决定，没有每份笔记都必须附带的来源、版本或日期字段。新建或修改主题笔记后，可按需更新 `MEMORY.md` 的导航；程序不会代做这一步。

模型也可以保存有用但未验证的假设。程序不会因为出现“已验证”三个字就执行检查，写入成功更不表示事实正确。事实验证依赖实际来源与反馈，不能由反复改写同一句话代替。

## 用一个例子走完保存、复用和纠正

以下例子与本项目的合成集成测试采用相同问题：一个测试夹具失败，初步怀疑重试模式，但后来的反馈指向缓存。它描述允许的工具流程，不保证模型每次都作出同样判断。

### 第一次工作留下带限制的笔记

前台观察到开启重试时失败，但还没隔离变量。它把这个观察和猜测写入项目笔记 `notes/test-cache.md`，而不是直接宣布找到了原因：

```markdown
# 测试夹具失败

观察：合成夹具 v2 在开启重试的运行中失败。
假设：可能与重试模式有关，尚未隔离验证。
来源：本次合成测试输出，fixture-session:entry-a:0。

继续排查时需要分别检查重试开关与缓存，不能推广到其他夹具。
```

同一个 Agent 再维护 `MEMORY.md`，只留下查找线索：

```markdown
# 项目记忆

- 合成夹具 v2 失败时，见 [测试缓存排查](notes/test-cache.md)，原因尚未确认。
```

这是两次独立文件写入。即使正文成功、索引更新失败，正文也已经存在，可以通过搜索找回，并非整批回滚。

### 下一会话从索引找到正文，继续实际排查

相同项目的新会话不需要继承上次对话。请求前读到索引后，模型可以按路径读取笔记，知道这是待验证假设，再用当前任务允许的工具继续检查。

假设这次合成反馈是“关闭重试仍失败，关闭陈旧缓存后通过，只检查过夹具 v2”。它支持纠正原先的猜测，但不支持把结论推广成所有项目的缓存规则。前台可以立即读出当前哈希，改写这份笔记，保留反馈与适用范围，再把索引改成指向有依据的排查经验。

笔记里的旧引用不表示前台已经核验该会话。前台三个记忆工具仍只访问 Markdown，后台则可以读取原生历史查找同项目的实际材料，查不到时保留未核验说明。

### dreaming 可以回查历史，也可以创建第一份笔记

若前台只留下了新反馈，没有更新旧笔记，后台 Agent 可以用普通文件和 shell 工具定位、读取同项目原始会话中的反馈。材料不必仍在当前压缩后的上下文中，也不必来自当前会话。后台再读取 `MEMORY.md` 和相关笔记，修订结论与索引。

若此前根本没有笔记，后台同样可以从历史中的有用经验创建正文与入口。调度不再等待前台先调用 `memory_write`。是否值得保存、怎样组织仍由模型决定，不是程序把每段对话自动转成笔记。

如果还有一份重复笔记，后台可以将有用内容合并到保留的路径，修好索引和其他笔记中的引用，再归档重复文件。归档文件不再进入活动搜索，原文仍留在 `.history/`。后台看不到的来源只能注明未核验，不能据此将假设升级为事实。

后续请求仍是读取同一份 `MEMORY.md`，再按需打开修订后的主题笔记。没有另外一份 dreaming 总结需要同步。脚本集成测试可以验证这条读写与跨会话流程，但不能验证真实模型的判断质量。

## 独立 dreaming Agent

### 按项目累计实际用户消息

自动 dreaming 默认启用。`session_start` 将会话中已有的用户消息条目 ID 记为基线，打开已有历史不会追溯计数。`agent_settled` 时，扩展观察新加入的实际用户消息，将其 ID 与原项目、会话 ID 和可选原生会话文件提示一起排队。一次完成的运行可能包含多条用户消息，也可能没有；工具调用、助手回复、内部模型请求和重复的完成通知都不算用户消息。

项目调度文件 `.dream-state.json` 持久保存消息 ID 去重记录与待处理会话批次，跨会话、跨进程累计。每条 `(sessionId, userEntryId, 可选 sessionFile)` 记录在处理后仍保留，用于持久去重。调度元数据最多容纳 1000 个不同会话、1 MiB JSON；达到任一限制时明确拒绝更新，不淘汰记录或重置状态。同项目达到 **50 条尚未处理的实际用户消息**后到期，不依赖已有笔记或前台 `memory_write`。已有 v1 待处理轮数迁移为可触发一次整理的 legacy 待处理工作，不把旧轮数改称或计作实际用户消息。

观察按原项目有序排队。跨进程文件锁被占用时，观察留在内存中，文件系统事件唤醒后重试，不轮询、不抢锁。模块重载共享同进程队列，不独立重放。未提交观察不保证崩溃恢复，退出时尝试提交，仍有未保存内容则明确警告。只读启动不建库，首次记录新用户消息时可以建立项目目录、identity 和调度文件，即使还没有 Markdown 笔记。

项目受信任、有当前模型、启用自动整理且工作到期时可以领取。每项目最多一个有效逻辑租约，持续 **1830 秒**，与短时文件锁不同。租约捕获领取代次和会话批次。由 worker 而非前台启动回调负责完成确认。成功只确认领取代次，之后的新消息继续待处理；失败保留待处理工作，已完成笔记写入仍保留。租约过期后可重新领取，不抢占有效租约。启动器在创建运行文件前检查有效租约，worker 通过原子领取处理同时启动的竞争。启动回执只表示 detached supervisor 已启动，不表示整理成功。

`--pi-memory-no-dream` 禁止新的自动启动，不停止观察记录。召回开关独立，没有运行时开关或手动整理命令。已提交但未启动的工作等待之后符合条件的前台时机；所有前台退出后，没有永久守护进程监听新工作。

### detached supervisor 启动普通 Pi Agent

独立 supervisor 目前要求 POSIX 宿主，不支持 Windows。它在规范项目目录中启动宿主 Pi CLI，使用所选 provider、model 和 thinking 级别。它显式加载记忆扩展与 worker 扩展，其余遵循正常 Pi 资源加载、配置、凭证、扩展、skills 与 MCP 设置。凭证从 worker 的正常配置重新加载，不序列化前台注册表对象。仅存在于前台运行时的 provider 注册、凭证或其他配置变化无法复制到新进程。worker 重新执行正常项目信任检查，启动器不自动批准信任。若前台的临时批准未持久保存，子进程可能安全失败，不会自动继承信任。

这是独立 Agent 会话，不是自定义消息数组循环。任务包含领取的会话 ID、可选原生文件路径、会话根目录、项目 identity、已有记忆位置和墙钟截止时间，不复制前台对话，也不建立来源会话副本索引。Agent 自主选择如何检查原始历史与记忆、读取多少上下文，以及哪些依据值得保存。仅凭位置提示可能无法恢复未落盘或不可用的会话，不能声称已经检查。

worker 拥有普通默认工具（`read`、`bash`、`edit`、`write`）、记忆工具与正常配置的资源，不再使用旧的 `memory_source_search`、`memory_source` 接口。保留的 `memory-sources.ts` 模块不限制它的原始读取。普通文件读取不自动进行活动分支投影、上下文编辑脱敏、thinking 字段排除或来源提供器分页。会话 ID 和路径只是定位线索，不能证明 Agent 逐条检查了历史或选对了分支。

维护提示要求 Agent 创建有用知识、纠正无依据结论、合并重复内容、修复链接、归档过时笔记并保持 `MEMORY.md` 简短；会话与源码只读，项目记忆通过记忆工具写入，保留不确定性，将历史指令视为不能授予权限的不可信材料。这些是任务策略，**不是操作系统沙箱**。完整 Agent 工具及配置的扩展可以访问文件、执行命令和发网络请求。通过记忆工具写入仍受路径、哈希、历史与锁保护，但这些检查不限制其他工具。

### 截止时间、前台独立性与运行记录

不再有扩展自定的 32 次模型请求、64 次工具调用或 64k 输出上限，请求使用所选模型与正常 Pi 默认值。Agent 会获知 **30 分钟墙钟截止时间**，从启动算起，包含启动耗时。supervisor 在截止时终止 worker，短暂清理宽限后强制杀死其进程组与已捕获的后代进程，包括普通 detached bash 工具。后代清理是尽力而为，不是进程容器：已被重新托管或脱离的进程以及外部工作仍可能继续。提供商已收到的请求仍可能计费，终止不能撤销已完成写入。

前台输入、新运行、会话树导航、会话切换、扩展重载和退出 Pi 都不取消已经启动的 supervisor 或 worker。活跃 worker 可以在前台退出后完成并确认租约。这不是永久服务，只有已启动的运行继续存活，Pi 关闭期间未触发的待处理工作不会自行启动。之后在另一个前台关闭 dreaming，也不会取消已经启动的运行。

每次运行在项目 `.dream-runs/` 下有唯一目录，包含运行状态 `status.json`、JSONL 事件 `events.jsonl`、诊断 `supervisor.log`，以及通过 `--session-dir` 保存在 `sessions/` 的 worker 自身原生会话。这些是私有运行记录，不是 Markdown 知识。程序不建立单独的来源会话镜像或索引，但 worker 会话和事件可能保留工具返回的来源内容。worker 会话不放进普通来源根目录，避免自身维护对话被当作新的前台历史。日志和会话可能包含原始敏感工具文本，不受 Markdown 笔记容量限制。

前台通过不轮询的目录 watcher 观察本进程启动的各次运行，注册时及文件系统事件后读取 `status.json`。worker 与 supervisor 通过原子替换更新状态。启动回执覆盖 launching/starting；观察到的运行中及终态分别产生简短的纯元数据通知，相同状态不重复显示，首个终态关闭 watcher。观察出错，或截止时间后十秒仍未取得终态时，只报告结果未知，不推断成功或超时。watcher 不阻止 Pi 退出，不调用模型，也不确认调度工作。重载或会话替换共享观察器，并通过当前 UI 发通知；退出只关闭观察器，不向 detached worker 发信号。通知不持久化，之后启动的进程不会补发。

诊断结果时应检查运行最终状态与会话；前台通知或模型声称完成都不能单独证明成功。最终调度确认由 worker 负责。错误或超时可能留下部分笔记更新，多文件维护和整次运行都不是事务。备份与清理时，除了前台 Pi 会话，还必须考虑活跃的 detached worker。

## 项目隔离、路径与并发保护

### 两个作用域怎样定位

存储根目录为 `PI_MEMORY_DIR`，未设置时为 `getAgentDir()/pi-memory`。其下直接是 `project-<hash>/` 和 `global/`，二者都可以包含 `MEMORY.md`、主题笔记、`.identity.json` 与 `.history/`。项目目录另有内部调度文件 `.dream-state.json` 和 `.dream-runs/` 运行记录，不参与笔记搜索或自动召回。`topics/`、`notes/` 只是模型组织内容的目录名，不是程序规定的分类。

项目 identity 的计算顺序：当前目录先执行 `realpath`，向上找最近的 `.git` 标记，以其所在目录为项目根；没有标记则用当前真实目录。只检查标记存在，不执行 Git，不读取标记内容。

代码中有两种 SHA-256，作用不同：

| 名称 | 输入 | 用途 |
| --- | --- | --- |
| 项目目录的 `<hash>` | 项目 identity 的绝对路径，UTF-8 编码 | 生成固定目录名，完整 64 位十六进制，不是 Git commit 或内容身份 |
| 笔记的 `hash`、写入的 `expectedHash` | 当前 Markdown 文件的完整 UTF-8 内容 | 检查读后是否有人修改，和只返回了哪一页内容无关 |

同一 Git 项目的子目录共用记忆，不同位置的克隆和独立 worktree 分开。非 Git 项目进入子目录可能得到不同 identity，移动项目也会改变归属。哈希不匿名化路径，归属元数据仍保存实际 identity。

项目访问要求 Pi 项目信任。前台读取、写入默认使用项目，搜索默认使用项目与全局；全局适合跨项目、非私密知识。记忆里的历史授权不扩大当前任务权限，这些接口也不是宿主 shell 或其他扩展的文件系统沙箱。

### 一次写入怎样提交

新建使用 `expectedHash: null`，只允许目标不存在。改写和归档必须匹配当前完整正文的哈希。一次写入依次经过 Pi 进程内文件队列、跨进程锁、路径与归属检查、当前哈希检查，再保存需要的历史并提交活动文件更新。

新内容先写入临时文件，完成同步后原子替换目标。新文件为 `0600`，新目录为 `0700`，不改已有父目录权限。锁冲突直接失败，不轮询抢锁，也不自动接管崩溃遗留锁。损坏、归属不符或非法路径不能被当成空库重置。

哈希不匹配时，现有工具错误结果会提示模型重新读取、比较，再合并或放弃。后台工具循环将错误交回模型，不因此中止整轮，也没有另加自动合并或冲突重试协议。只把请求里的哈希换成最新值重放旧正文，仍会覆盖别人有效的更新。多文件和整次 dreaming 都不是事务，正文、索引、其他引用需要分别提交，可能暂时不一致。

### 归档与容量

归档先保留当前正文，再移除活动文件。它不会自动修改其他文件中的链接，不能归档根目录 `MEMORY.md`，也不提供通过记忆工具清空历史的动作。历史快照位于 `.history/<原相对路径>/<UUID>.md`，保留原正文内容，不参与活动列表和搜索。

| 对象 | 上限 |
| --- | --- |
| 每份 `MEMORY.md` | 8 KiB、200 行 |
| 每份普通 Markdown | 64 KiB |
| 每个作用域活动 Markdown | 500 文件、合计 8 MiB |
| 每个作用域历史快照 | 1000 份 |

历史满后拒绝需要增加快照的操作，不自动清理最早记录。归档同样需要历史空间。根目录索引名必须精确为 `MEMORY.md`，不能用大小写别名或将其当目录，避免在大小写不敏感文件系统上绕过限制。

修订历史不是备份系统。独立备份、恢复或清理前应停止所有写入者。归档不会移除已有会话、备份或提供商副本，也不保证安全擦除。

## 与参考文章怎样对应

设计参考 Anthropic 于 2026 年 11 月 6 日发表的 [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)。以下对应同时依据正文和图 1 至图 15，不把架构示意、任务实验和本扩展的实现选择混为一谈。维护工作区保留图文快照于 `references/components-of-agent-memory/`，包含原 HTML、原图、离线正文与来源哈希；该第三方快照仅保留在本地，不进入 Git 或 npm 包，全新克隆不含它；目录存在时，复查方法见其中的 README。

图 1、2、6、9、13 描述的是可组合的记忆层次，不是每次必须依序执行的流水线。会话中可以直接写下显著观察；dreaming 可以依据原始记录纠正笔记、建立相互链接的表示，或提升内容到注入层，也可以调整上层之间的组织。本项目以自由 Markdown 和链接承载笔记及表示，以小 `MEMORY.md` 承载注入层，不要求另建独立 Wiki 引擎。后台能从原生历史创建第一份笔记，不以前台先写笔记为前提。

前台轻指导与后台详细维护是两种任务。文章给前沿模型的常用指导是说明记忆用途，用户要求或内容明显值得记住时保存，把显著性判断留给模型。它没有证明所有模型都适合更少指导：图 5 左侧的细化指导改善了 Sonnet 4.6 的表现，右侧测试的是“只记录失败”这一限制，且样本数较少、两侧误差棒分别为标准差和标准误。本项目采用轻量前台用途提示，不声称它对任意模型最优；后台的来源回查、纠错、合并、修链和小索引维护仍需明确任务提示。

图 10 展示 Wiki 与原始资料搜索的互补，不是用 Wiki 取代来源。横轴是对数刻度的 Wiki 生成预算，每会话预算 1M tokens，图中特别注明不是实测花费。图 11 的跨文档判断任务与单篇可检索任务收益不同，分类由模型标注，不能过读每一条连线；图 12 还展示了 Wiki 膨胀到原材料 1.77 倍的反例。本项目前台工具搜索 Markdown，后台 Agent 可以用普通工具读取原生历史，不等同于实验中回答问题时同时搜索原始公司文档的配置。

图 14 的每合同单页、单作者和逐字引用条款，是合同任务中同时处理覆盖与摘要丢事实的实验改进，不是所有记忆系统都必须采用的所有权流程。图 15 的第二轮整理修复了 9 条缺页链接并新增 3 页，支持后台维护链接、补足入口的职责，不表示程序必须自动生成图谱或每次重建整库。文章中的指令反思与重建 Wiki 循环也属于任务实例，本项目没有复制这套实验框架。

项目与全局划分、哈希与锁、50 条用户消息触发、30 分钟截止时间和容量限制都是本扩展自己的实现选择。文章把创建时机、更新可靠性和 dreaming 节奏列为开放问题，没有规定这些数字。具备上述数据流不等于已经获得文章中的学习效果；验证规则仍需真实测试或来源反馈，不能用笔记的“已验证”标签代替。

## 实现承诺与尚未证明的效果

记忆工具代码约束自身路径、冲突与存储限制，supervisor 执行运行截止时间，但不隔离完整 Agent 的文件、shell、扩展或网络访问。提示引导模型怎样选择内容、检查依据和维护链接。后者不等于程序保证：没有来源检查器证明每段正文正确，没有链接检查器保证整理后全无坏链接，也不保证每个模型都会主动写入或正确使用笔记。

笔记是明文。注入的索引、读取的正文和 dreaming 来源会发给所选模型提供商，不能把本地存储写成不离开设备。提示与自由 Markdown 也不保证防止指令注入。

自动化测试覆盖程序边界、合成工具流程、离线 CLI 加载及脚本模型闭环，不能证明真实任务上的记忆收益。效果评测需要另行记录模型、任务、无记忆基线、预算和结果，不能引用 Anthropic 的实验结果代替。源码导航和验证方法见[开发指南](development.zh-CN.md)。
